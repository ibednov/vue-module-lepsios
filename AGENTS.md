# Universal CRM agent rules

Работай в рамках конкретного продукта, сохраняя его маршруты, авторизацию, API и пользовательские возможности. Общие сущности и UX сверяй с этим репозиторием. Не переносить чужую бизнес-логику только потому, что совпало название модуля.

## Перед изменением

1. Найди проектные `AGENTS.md`, проверь рабочее дерево и сохрани незакоммиченные изменения пользователя.
2. Определи роль репозитория: frontend CRM приложение, frontend microfrontend или host shell.
3. Сверь существующую сущность с `packages/contracts` и `schemas`; зафиксируй отличия как расширение, не меняй смысл текущих данных.
4. Проверь фактические API операции и permission checks. Скрытая кнопка не является авторизацией.

## Общие модели

- Общие поля и семантика версионируются здесь. Не переименовывай поле или статус локально без адаптера/миграции и плана совместимости.
- Проектные данные размещай в расширениях с собственными схемами. Не добавляй nullable-поля для всех продуктов ради одного конкретного экрана.
- Идентификаторы внешнего API сохраняй как непрозрачные строки; даты передавай в ISO 8601 UTC.
- Модель, DTO, API и БД не обязаны иметь одинаковую форму. Преобразование находится в адаптере/маппере.
- CRUD и статусы остаются у каждого продукта, если у API нет операции. Не придумывай UI для неподдерживаемых операций.

## UI контракт

- Списки сущностей используют общий табличный паттерн с заголовком страницы, количеством, поиском/фильтрами, сортировкой/пагинацией по возможностям API, loading, empty и error states. Карточный обзор допустим для dashboard, Kanban — как явный переключаемый вид доски.
- Если API и бизнес-процесс поддерживают ручное создание, оно открывается на отдельном `/create/` маршруте. Не придумывай ручной create для сущностей, которые рождаются из конверсии или consent-процесса. Inline-формы не используй для создания основных CRM-записей.
- Детали и редактирование имеют собственные маршруты (`/:id/`, `/:id/edit/`) либо явно согласованный продуктовый паттерн.
- Действия строки сгруппированы в dropdown/overflow menu. Основное действие может быть выделено отдельно. Удаление и отзыв ключа имеют подтверждение и destructive-стиль.
- Роли, статусы и типы показываются читаемыми badge/chip-компонентами, не сырой строкой с машинными enum.
- Одинаковая таблица должна иметь одинаковые плотность, отступы, заголовки, мобильный режим, empty/error/loading states. Не скрывать таблицу на desktop или растягивать фильтры без причины.
- Ширина содержимого соответствует типу страницы: рабочие списки занимают рабочую область; формы читаемы и не центрируются в огромном пустом холсте; узкие настройки используют согласованный `max-width`.
- Длинные идентификаторы и пользовательские значения переносятся; контент не должен сдвигать action-колонки.
- Все видимые строки интерфейса локализованы. API ошибки показываются в соответствии с правилами конкретного API; не выводить сырые технические ошибки вроде `Failed to fetch` без понятного состояния и повторной попытки.

## Структура модуля

Новый продуктовый модуль — frontend вертикальный срез: типы, API-адаптер, состояние/композаблы, страницы list/create/detail/edit, локализация и permission mapping. Этот шаблон не задаёт структуру backend-репозитория.

Не вводи новый UI kit, таблицу или меню действий, если проект уже использует общий компонент. Для новых таблиц следуй `docs/ui-contract.md`.

## Проверка и доставка

- Не запускай тесты, если пользователь явно не просил. Build/typecheck запускай, когда они нужны для проверки сборки и не противоречат инструкциям проекта.
- Для общих контрактов обновляй версию и changelog; миграции данных должны быть обратно совместимыми.
- Не добавляй локальные абсолютные пути в production manifests.
- Не коммить и не пушь без действующих инструкций проекта/пользователя; push только по явному запросу.
