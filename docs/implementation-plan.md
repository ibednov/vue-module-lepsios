# План общей библиотеки CRM-модулей

Дата сверки: 2026-10-25

## Назначение репозиториев

- `vue-lepsios` — общие Vue UI-компоненты без продуктовых правил.
- `vue-module-lepsios` — подключаемые CRM feature-модули, их публичные типы и интерфейсы API-адаптеров.
- Первые потребители и источники поведения: Concierge CRM, Spending CRM, Wishimi CRM и Go Product CRM.
- `edu-markdown-test/apps/web` — источник полезных UX и архитектурных решений; проект не мигрируем.
- Yarmarka не входит в первую волну.

Хост-приложения сохраняют свои роуты, аутентификацию, API, права, предметные типы и тексты. Общий модуль не должен подменять продуктовую политику или считать одинаковыми сущности только из-за совпадения названия.

## Этапы

### 1. Сверить и выделить общий табличный UI

Сопоставить `CrmDataTable` в `vue-lepsios`, таблицу Concierge, Spending, `TableShell` Wishimi и использование таблицы Go Product. Зафиксировать общий API и отличия: серверные поиск/сортировка/пагинация, выбор строк, действия, ошибки и retry, пустое и loading-состояния, slots для ячеек и локализованные подписи.

UI-реализация остаётся в `vue-lepsios`. В `vue-module-lepsios` не копировать shadcn-vue primitives и разметку таблицы. Подключать потребителей по одному, сохраняя серверные операции и пользовательские возможности.

Статус на 2026-10-25: adoption по таблице отмечен для всех четырёх первых
потребителей в `adoption-status.md`; продуктовые таблицы с inline-редактированием
или особой мобильной композицией оставлены на месте.

Порядок потребителей: Concierge, Spending, Wishimi, Go Product CRM. Go Product уже использует `CrmDataTable` из `vue-lepsios`; там сначала проверить, каких возможностей общего компонента не хватает, и не делать повторную миграцию.

### 2. Проверить модуль журнала событий

Для Concierge, Spending, Wishimi и Go Product сравнить модель события, список операций чтения, фильтры, пагинацию, локализацию и permission checks. Выносить `audit-log` только в пределах совпадающего контракта; поля и фильтры продукта оформлять адаптером/конфигурацией.

Статус на 2026-10-25: нормализованный HTTP DTO и GET-контракт сверены с
`go-lepsios/audit` и существующими endpoints Concierge API, Spending API,
Wishimi backend и Go Product site-api. Хосты сохраняют auth, permission checks,
route registration и storage. Новый общий backend endpoint не требуется.

### 3. Общие roster и каталог доступа

Read-only roster вынесен в `@lepsios/crm-team-members` для Concierge и Spending. Общий контракт не включает создание staff, приглашения, назначение ролей или удаление: эти операции остаются в хостах. Read-only каталог ролей и разрешений вынесен в `@lepsios/crm-access-control` для Spending и Go Product CRM. Авторизация и мутации ролей остаются в хостах. Wishimi users и Go Product customer accounts не считаются сотрудниками CRM; enum roles Concierge не образуют каталог permissions.

Статус на 2026-10-25: adoption matrix подтверждён, для обоих контрактов
добавлены примеры host-owned DTO mapping.

### 4. Входящие обращения (отложено)

Сначала определить общий предметный процесс и границы. Не использовать `inquiries` как имя по умолчанию и не включать Concierge Lead qualification/Application conversion в модуль входящих обращений без подтверждения совместимости.

## Версии и подключение

Каждый готовый модуль — отдельный пакет в `vue-module-lepsios` с собственным semver и changelog. Имя должно обозначать предметную возможность, а не продукт или личный бренд; npm scope должен принадлежать библиотеке. Потребитель подключает только используемый модуль и фиксирует его версию.

Пакеты имеют отдельные semver manifests, но пока доступны только из исходного
репозитория и не опубликованы в registry.

Сначала завершать и фиксировать каждый модуль или интеграцию отдельным коммитом в соответствующем репозитории. Не пушить без явного разрешения пользователя.

## Критерии готовности модуля

1. Есть минимум два подтверждённых потребителя среди четырёх целевых CRM.
2. Сверены реальные API операции и проверки прав.
3. Продуктовые DTO преобразуются адаптерами; статусы, permissions и валидация не зашиты в общий модуль.
4. У каждого потребителя сохранены текущие маршруты и возможности.
5. Есть короткий пример подключения, changelog и независимая версия пакета.
